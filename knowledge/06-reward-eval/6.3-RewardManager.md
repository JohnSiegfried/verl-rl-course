# 6.3 RewardManager：naive / prime / dapo / limit / remote / reward_loop

## 一句话
RewardManager 负责把你的 `compute_score` 并行、高效地跑在一批 response 上：从最简单的逐条串行（naive），到进程池并行（prime）、CPU 密集隔离（remote）、API 限流（limit），再到分布式 RewardLoop——按 reward 的成本选对管理器。

## 核心公式/原理

### RewardManager 的统一接口
所有 reward manager 都是可调用对象：
```python
manager(data: DataProto, return_dict: bool = False) -> Tensor | dict
# return_dict=True → {"reward_tensor": ..., "reward_extra_info": ...}
```
- 输入：含 rollout 轨迹的 DataProto（[[3.2-DataProto格式]]）。
- 输出：`reward_tensor`，非零项标记每条 response 的标量奖励（通常落最后一个 token，[[3.4-数据流转全链路]]）。

### 六种实现对比
| Manager | 执行方式 | 适用 | 备注 |
|---|---|---|---|
| **naive** | 进程内逐条串行 | 简单/调试 | 慢，batch 大时是瓶颈 |
| **prime** | `ProcessPoolExecutor` 并行 | 高吞吐训练 | 多进程并行打分 |
| **dapo** | 含 overlong penalty | DAPO 算法 | 超长截断软惩罚（[[6.4-reward hacking]]） |
| **limit** | 限制并发数 | 外部 API 打分 | 防 API 超速率限制 |
| **remote** | 独立进程 | CPU 密集（如 Math-Verify） | 隔离 CPU 密集计算 |
| **reward_loop** | 分布式多 worker | 大规模/混合 reward | verl 默认新实现（见下） |

### naive vs prime（最常用的两个）
```python
# naive：逐条 for 循环，简单可调试
NaiveRewardManager(tokenizer, num_examine=2, compute_score_fn=...)

# prime：进程池并行，高吞吐
PrimeRewardManager(tokenizer, num_examine=2, compute_score_fn=...)
```
- `num_examine`：每个 data_source 打印多少条 prompt/response/score 用于调试（下面有示例）。
- **选择**：调试期用 naive 看清单条；正式训练用 prime 提吞吐。

> [!note] 调试输出示例（num_examine 控制）
> ```
> [prompt] Solve the quadratic equation: x^2 - 7x + 12 = 0
> [response] The solutions are \boxed{x=3, x=4}
> [ground_truth] x=3, x=4
> [score] 1.0
> ```
> 训练初期务必开 num_examine 看几条，确认 reward 打分符合预期——很多"reward 不涨"其实是打分函数写错了。
> 来源：verl reward manager 源码。

### RewardLoop：分布式 reward（verl 默认新实现）
对大规模训练，reward 计算也可分布式。架构：
```
RewardLoopManager（单控制器内）
  ├─ 启动多个 RewardLoopWorker（跨节点）
  └─ compute_rm_score(data):
        chunks = data.chunk(len(workers))     # 切 batch
        ray.get([w.compute_score_batch.remote(c) for ...])  # 并行
```
- `config.reward.num_workers` 控制并行 worker 数。
- 每个 RewardLoopWorker 内部：把 batch 拆成单条，用 `asyncio` 并发调 `compute_score`。

**流式 reward（与 rollout 重叠）**：当满足 ①规则奖励 或 ②RM 有独立资源池时，reward 可与 rollout **流式并行**——一条样本 rollout 完立刻算 reward，不等整批：
```python
enable_agent_reward_loop = (not use_rm) or config.reward.reward_model.enable_resource_pool
```

### RewardLoop 的奖励分发逻辑
```python
async def compute_score(self, data):
    if config.reward.custom_reward_function.path is not None:
        return await self.reward_manager.run_single(data)   # 自定义函数
    else:
        if config.reward.reward_model.enable:
            return await self.compute_score_disrm(data)      # DisRM
        else:
            return await self.reward_manager.run_single(data)# 规则
```
> 优先级：**自定义函数 > DisRM > 规则**。GenRM 必须走自定义函数。
> 来源：verl Reward Loop 文档（逐字逻辑）。

### 怎么选
```
reward 是规则（快、免费）？
  ├─ 调试期 → naive
  └─ 训练期 → prime（或 reward_loop）
reward 要调外部 API（GPT 评判等）？
  └─ limit（限流）
reward 是 CPU 密集计算（Math-Verify）？
  └─ remote（独立进程隔离）
reward 是 RM（DisRM/GenRM）或混合？
  └─ reward_loop（分布式 + 可流式）
DAPO 算法？
  └─ dapo（含 overlong penalty）
```
