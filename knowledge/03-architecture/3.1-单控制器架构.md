# 3.1 verl 单控制器架构：Ray + Worker 抽象

## 一句话
verl 把"RL 算法逻辑（控制流）"放在**单进程**里，把"模型前向/反向（计算流）"放在**多进程 Worker** 里，通过 Ray 调度——控制流想怎么改就怎么改，计算后端想换 FSDP 还是 Megatron 也不用动算法。

## 核心公式/原理

### 设计动机：RL 是两层数据流问题
RLHF 与传统神经网络训练的数据流有本质区别：

| | 节点 | 边 |
|---|---|---|
| 神经网络训练 | 算子（matmul/softmax） | 张量流动 |
| **强化学习** | **高层算子**（rollout/模型前向） | **数据流动** |

所以 RL 是个**两层数据流**：
- **控制流**：高层算子的执行顺序（先 rollout → 再算优势 → 再 update）→ 表达 RL 算法逻辑。
- **计算流**：单个高层算子内部的神经网络前向/反向 → 用 FSDP/Megatron 跑。

> [!important] 两种解耦方案，verl 选了后者
> 1. **统一多控制器**：控制流也多进程，与计算流 colocate。性能最优但代码耦合、难复用。
> 2. **分离（verl 采用）**：控制流单进程 + 计算流多进程。计算后端可复用、改算法简单，代价是控制进程与计算进程间的数据通信开销。
> 来源：HybridFlow 论文与 verl HybridFlow Guide。

### 核心角色：3 类 WorkerGroup
在 PPO 中，verl 定义 3 个 WorkerGroup（每组管理一组跑在 GPU 上的远程 Worker）：

| WorkerGroup | 管理的模型 | 说明 |
|---|---|---|
| **ActorRolloutRef** | actor + rollout + reference | 三者 colocate 在同卡：actor/rollout colocate 是为 NCCL 快速传权重；actor/ref colocate 是为高效 LoRA（ref 即 base model） |
| **Critic** | critic 模型 | PPO 用；GRPO 无 |
| **Reward** | reward 模型 | RLHF 用；RLVR 规则奖励不需要 |

> [!note] colocate 的实现
> 用 `verl.single_controller.ray.base.create_colocated_worker_cls` 把多个角色的方法合并进**单个 Ray remote class**，使它们共享同一张 GPU。这是 RL 多模型省显存的关键（配合 [[1.5-显存分配精算]]）。
> 来源：verl HybridFlow Guide（Worker 定义）。

### 单进程主循环长什么样
verl 的 PPO 主循环写出来**就像单进程程序**（实际上每个 `*_wg.xxx()` 都是远程调用）：

```python
for prompt in dataloader:
    output      = actor_rollout_ref_wg.generate_sequences(prompt)   # rollout
    old_log_prob = actor_rollout_ref_wg.compute_log_prob(output)    # 当前 actor
    ref_log_prob = actor_rollout_ref_wg.compute_ref_log_prob(output)# 参考模型
    values       = critic_wg.compute_values(output)                 # critic（PPO）
    rewards      = reward_wg.compute_scores(output)                 # reward
    advantages   = compute_advantages(values, rewards)              # 控制进程本地算
    output = output.union(old_log_prob).union(ref_log_prob)\
                    .union(values).union(rewards).union(advantages) # 合并进 DataProto
    actor_rollout_ref_wg.update_actor(output)                       # 更新 actor
    critic_wg.update_critic(output)                                 # 更新 critic
```
> 控制进程是 `main_task`（在 `main_ppo.py`），`RayPPOTrainer.fit` 也是单进程。数据容器是 DataProto（[[3.2-DataProto格式]]）。
> 来源：verl HybridFlow Guide（PPO main loop）。

### dispatch 语法糖：@register
控制器调用 WorkerGroup 方法时，底层自动做三件事：**数据切分 → 分发到各 Worker → 收集拼接**。用装饰器声明切分方式：

```python
@register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)
def generate_sequences(data): ...

# 控制器端一句话，背后自动 split/dispatch/collect：
output = actor_rollout_ref_wg.generate_sequences(data)
```
`Dispatch.DP_COMPUTE_PROTO`：把 DataProto 按 DP 切分发给各 Worker，算完 cat 回来。这要求输入输出都是 DataProto。

> [!warning] main_task 别调度到 Ray head
> `main_task` 消耗大量内存，而 Ray head 通常资源很少。官方建议 main_task **不要**放在 head 节点。
> 来源：verl HybridFlow Guide。
