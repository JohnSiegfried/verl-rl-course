# 3.5 batch size 体系：train / rollout.n / mini / micro / 动态 bsz 归一化

## 一句话
verl 的 batch 是**强约束、可验证、有日志**的四级体系：`train_batch_size`（全局 prompt）→ `×rollout.n`（总 response）→ `ppo_mini_batch_size`（每次 actor 更新）→ `*_micro_batch_size_per_gpu`（每卡每次前向）；满足整除约束就能从配置一路推到每张卡的实际负载。

## 核心公式/原理

### 四级 batch 一览
| 层级 | 参数 | 作用域 | 含义 |
|---|---|---|---|
| L1 全局 | `data.train_batch_size` | 全局 | 一步处理多少个 **prompt** |
| L2 采样 | `actor_rollout_ref.rollout.n` | 全局 | 每 prompt 采 **n** 条 response |
| L3 更新 | `actor_rollout_ref.actor.ppo_mini_batch_size` | 全局 | 一次 actor 更新用多少条 response |
| L4 前向 | `*_micro_batch_size_per_gpu` | **每卡** | 每卡每次前向/反向的序列数 |

**总 response 数（全局）**：
$$B_{total} = \text{train\_batch\_size} \times \text{rollout}.n$$

> [!important] 算法量 vs 性能量（关键认知）
> verl 官方原则：
> - **算法相关量**（train_batch_size、ppo_mini_batch_size）是**全局**的（单控制器视角），在每个 Worker 内归一化。
> - **性能相关量**（`*_micro_batch_size_per_gpu`、动态 bsz 的 max token）是**局部**的，定义每卡的数据分配。
> 用 `*_micro_batch_size_per_gpu` 而不是 `*_micro_batch_size`（后者会被归一化、即将废弃）。
> 来源：verl Performance Tuning Guide。

### 整除约束（OOM/报错前先看这里）
```
① train_batch_size × rollout.n  必须能被  world_size(GPU 数) 整除
② 总 response 数 必须能被  ppo_mini_batch_size 整除
③ ppo_mini_batch_size / world_size  =  每卡 mini batch
④ 每卡 mini batch  必须能被  micro_batch_size_per_gpu 整除
```

> [!danger] 最常见的报错
> `ppo_mini_batch_size should be larger than 0 after normalization`
> → 根因：`train_batch_size × rollout.n` 不能被 world_size 整除。
> → 解法：调 `rollout.n` 或 `train_batch_size`，使乘积可被 GPU 数整除。
> 来源：verl batch 机制分析（见关键来源）。

### 完整推导实例（照抄 verl 社区案例）
配置：`train_batch_size=60`、`rollout.n=12`、6 卡、`tensor_model_parallel_size=2`（TP=2，则 DP=3）、`log_prob_micro_batch_size_per_gpu=8`：

| 阶段 | 计算 | 每卡/每组数量 |
|---|---|---|
| Input prompt | 60 ÷ 6 × 2(TP) | 每 TP group 20 条 prompt |
| Rollout output | 20 × 12 | 每 TP group 240 条 completion |
| Global rollout | 240 × 3(DP) | 全局 720 条 |
| Actor update batch | 720 ÷ 6 | 每卡 120 条 |
| Log prob micro-batch | 设 8 | 每卡每次 8 条算 log_prob |

> 从用户配置的 60，到每卡 120 的更新 batch、8 的 micro-batch，全程有码可查（归一化在 `fsdp_workers.py` 的 `__init__` 有 assert 和 print）。
> 来源：verl batch 机制分析（逐字案例）。

### 动态 batch size（use_dynamic_bsz）
变长序列时，按"固定序列数"组 batch 会浪费或爆显存。动态 bsz 改为按**token 数**组 batch：
```
actor_rollout_ref.actor.use_dynamic_bsz=True
actor_rollout_ref.actor.ppo_max_token_len_per_gpu=<每卡 token 预算>
```
- 每个 micro-batch 的**总 token 数**≤ `ppo_max_token_len_per_gpu`，序列数随长度浮动。
- 长序列少放几条、短序列多放几条 → 吞吐更高、显存更稳。
- 配合 `use_remove_padding=True` 效果最佳。

### 调 batch 的经验顺序（配 [[4.5-OOM排查决策树]]）
1. **OOM 先调小 micro_batch**：`*_micro_batch_size_per_gpu` 是每卡显存的直接旋钮，从 32→16→8→4 逐级降。
2. **forward-only 的可以更大**：`ref.log_prob_micro_batch_size_per_gpu`、`rollout.log_prob_micro_batch_size_per_gpu`、`critic.forward_micro_batch_size_per_gpu` 只前向不反向，可设为训练 micro 的 **2×**。
3. **critic/reward 可比 actor 大**：actor 最后一层词表大（vocab 151936），显存更紧；critic/reward 词表小，micro 可更大。
4. **算法量（train_batch/mini_batch）影响的是"数据效率与稳定性"，不是单卡显存**——别拿它们当显存旋钮。

> [!tip] 黄金搭配（官方建议）
> 开 `enable_gradient_checkpointing=True` → 可以把 micro_batch 调大 → 减少反向次数 → 吞吐更高。显存换时间 or 时间换显存，由你的瓶颈决定。
> 来源：verl Performance Tuning Guide。
