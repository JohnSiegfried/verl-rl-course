# 4.5 OOM 排查决策树：rollout / log_prob / update 三阶段

## 一句话
verl 的 OOM 必定位到"哪个阶段"——rollout（vLLM 推理）、log_prob（前向算概率）、update（反向更新）——每个阶段的诱因和解法不同；按"先阶段、后旋钮"的顺序，90% 的 OOM 能在三次尝试内解决。

## 核心公式/原理

### 第一步：定位阶段（看报错栈）
| 阶段 | 报错关键词 | 该阶段的显存构成 |
|---|---|---|
| **Rollout** | vllm / generate / KV cache / gpu_memory_utilization | 推理权重 + KV cache |
| **log_prob** | compute_log_prob / forward / logits | 前向激活 + **大词表 logits** |
| **update** | backward / optimizer / update_actor | 训练态(16P/N) + 反向激活 |

> [!important] 为什么 log_prob 阶段特别容易 OOM
> 算 log_prob 要对**每个 token 输出整个词表的 logits**（Qwen3 vocab=151936）。一条 1024 token 的 response，logits 就是 `1024 × 151936 × 2B ≈ 300MB/条`（未优化时）。micro_batch 一大立刻爆。这是为什么 verl 有"entropy/logits 显存优化"（见 [[7.1-性能调优]]）。
> 来源：verl Performance Tuning Guide（memory optimization for entropy from logits）。

### 决策树（按阶段给旋钮，按优先级排序）

**🟥 Rollout 阶段 OOM**
```
1. gpu_memory_utilization ↓（0.6→0.5→0.4）   ← 最快
2. max_num_seqs / max_num_batched_tokens ↓     ← 减 KV 并发
3. max_response_length ↓                        ← 减 KV 长度
4. tensor_model_parallel_size ↑（若有空闲卡）    ← 权重切更碎
5. rollout.n ↓ 或 train_batch_size ↓            ← 减总序列
6. actor 参数 offload → 给 rollout 腾显存
```

**🟨 log_prob 阶段 OOM**
```
1. log_prob_micro_batch_size_per_gpu ↓（8→4→2） ← 最快最直接
2. 启用 chunked/fused logits 计算（省大词表 logits）
3. use_remove_padding=True + use_dynamic_bsz=True ← 减无效 token
4. max_response_length ↓
```

**🟩 update 阶段 OOM**
```
1. ppo_micro_batch_size_per_gpu ↓              ← 最快
2. enable_gradient_checkpointing=True           ← 重算换显存
3. enable_activation_offload=True（仅 FSDP）
4. actor.fsdp_config.optimizer_offload=True     ← 优化器卸 CPU
5. actor.fsdp_config.param_offload=True         ← 参数卸 CPU
6. 换 LoRA（16P→2P，[[1.6-选模型选显卡实战]]）
```

### 通用排查三板斧
1. **先看 nvidia-smi 是哪个时刻涨满**：训练循环里 rollout 前后显存会"呼吸"（[[3.6-3D-HybridEngine]]），抓住涨满的那个 phase。
2. **micro_batch 是万能第一旋钮**：三个阶段的 OOM 都能先靠"调小对应 micro_batch"临时止血，再优化结构。
3. **整除约束别踩**：改了 batch 后检查 [[3.5-batch体系]] 的整除，否则 OOM 没解决先报 normalization 错。

### 报错速查表（社区高频）
| 报错/现象 | 根因 | 解法 |
|---|---|---|
| `ppo_mini_batch_size should be larger than 0 after normalization` | train_batch×n 不能被 GPU 数整除 | 调 n 或 train_batch 凑整除 |
| `CUDA out of memory in compute_log_prob` | log_prob micro 太大 | 调小 log_prob_micro_batch_size_per_gpu |
| rollout 阶段 GPU 利用率不均 | world_size 不能被 tp 整除 | 保证 `world_size % tp == 0` |
| gen_batch_output 形状不符 | rollout.n 被覆盖未生效 | 检查启动参数是否传对 n |

> 来源：verl batch 机制分析（速查表逐字）。

### 一个真实 OOM 排查示例
> 现象：8×A100 跑 8B，update 阶段 OOM。
> 排查：nvidia-smi 显示反向时显存冲顶 → 定位 update 阶段。
> 解法链：micro 32→16（仍 OOM）→ 开 gradient_checkpointing（仍紧）→ 开 optimizer_offload（解决）。
> 复盘：其实 [[1.5-显存分配精算]] 的预算表没留够激活余量，应该在跑前就把 ckpt 开上。
